> 副标题：当你的检查全绿、你的记忆库很大、你的交接文档很厚的时候，真正骗你的往往不是模型，是**验证层**。

> 这篇文章里的每个数字都能在本仓库找到出处。凡是仓库里没有的，我不写。

> **注**：标题里的「12 处矛盾」来自**另一个学习项目**；AHP 自己的冷读结果是 **8 / 3 / 5** 处。两件事的教训是同一条，所以放在一起讲。

## 一、一个全绿的仪表盘

先交代我做了什么，免得下面的"打脸"没有分量。

我做了一个仓库内的 Agent 交接协议，叫 **AHP（Agent Handoff Protocol）**，代号是"机器可检查的交接协议"。它不负责"记住更多"，它负责一件事：**当前状态是否可信，换人之后能不能接上。**

结构很简单，四个文件：

| 文件 | 职责 |
|---|---|
| `AGENTS.md` | Agent 入口、边界、交接契约 |
| `INDEX.md` | 文件地图，不放任何动态状态 |
| `PROJECT.md` | 长期决策 + 一个**派生**状态块 |
| `HANDOFF.md` | 当前工作单元、精确暂停点、下一动作、验收 |

再加一个状态机：`PAUSED → ACTIVE → PAUSED / BLOCKED / COMPLETE / MONITORING`。`ACTIVE` 必须带未来的租约；`PAUSED` 和 `COMPLETE` 不许留下 owner、session、租约残留（`SPEC.md` §3）。

然后是 **12 条门禁**，`node bin/ahp.mjs check` 一次跑完。下面是 v0.1.0 发布之后、我接管这个写作单元之前（状态 `PAUSED`、工作树干净）那一次的输出：

```
PASS CORE_FILES       core files present
PASS HANDOFF_SCHEMA   frontmatter is valid
PASS HANDOFF_TIME     timestamps are ordered
PASS LEASE            PAUSED has no residual lease
PASS VERIFY_COMMAND   verification command recorded
PASS HANDOFF_BODY     8 sections and next action are present
PASS HANDOFF_FRESH    sections 4-6 are fresh (0 days)
PASS INDEX_MAP        INDEX is a map and its links resolve
PASS PROJECT_SYNC     derived status matches HANDOFF
PASS MEMORY_LINKS     memory index and links are closed
PASS SECRETS          no high-confidence secret pattern found
PASS GIT_STATE        tree clean; timestamp matches the commit

[ahp] 0 FAIL / 0 WARN / 12 PASS / 0 SKIP
```

一个数字：fail-open 门禁。每条门禁都必须有一个**必须变红**的负向夹具，否则它只是声明，不是检查。整套东西当时 22 个测试：其中 15 个是"必须变红"的负向夹具（一条门禁一个），6 个是 CLI 和脚手架测试，1 个是正向的"合法项目应该全绿"。`npm test` 22/22。

> **这是 v0.1.0 的快照。** 写完这篇之后 `SECRETS` 门禁增加了 `docs/` 扫描，现在是 **27 个测试、19 个负向夹具**——数字变了，方法没变。

**顺带说一句**：写这个单元的时候仓库状态是 `ACTIVE`（我在干活），同一条命令的输出会不一样——`LEASE` 那行变成 `lease valid until ...`，`GIT_STATE` 变成一条 WARN（工作树是脏的，所以跳过提交日比对）。同一段代码、同一份配置，输出随状态变化。**门禁必须连着状态一起读**，这也正是我下面要讲的那类问题。

到这里为止，一切都对。

然后是那个让我坐直的数字。先说清楚它**属于谁**：这是**另一个学习项目**的冷读结果——它的门禁全绿，零上下文读手在四个核心文件里找出 **12 处矛盾**。而我自己的仓库，冷读结果是 8 / 3 / 5 处（下一节）。

零上下文读手要做的事只有一件：只给它四个核心文件，让它回答五个问题——当前工作单元和状态是什么、下一动作是什么、上次验证命令和结果是什么、三个最大风险是什么、四个文件之间有哪些矛盾。

那个学习项目的门禁是 **0 FAIL**。

## 二、门禁看不见的那些矛盾

先说被我审过的另一个项目（学习项目，脱敏）：7 个核心文件、3 个记忆文件、13 条门禁，**门禁全绿**，零上下文冷读在四个文件里找出 **12 处矛盾**（`docs/case-studies.md` 案例 8）：

- `current_file` 写着一个文件，正文 §3 却写"当前没有文件在编辑"；
- 验收标准在一个文件里写了 3 条、在另一个文件里写了 4 条；
- 同一个项目里有**三套**不同的验证命令；
- 摘要文件的"最后更新"表头，比它自己最新的一条记录还早 4 天；
- `INDEX.md` 一处写"地图和状态"，另一处写"只放地图"；
- 状态是 `ACTIVE`，但租约**已经过期 34 分钟**；
- 最后验证命令写的是一个**生命周期命令**（`ahp pause`），不是验证命令。

生产项目规模更大：70+ 记忆文件、279 条 wiki 链接、211 KB 的 `HANDOFF.md`、185 KB 的长期摘要、5 处派生镜像。它同样有同款问题——§1 写"已接受并推送"，§2、§5 和 frontmatter 还在说"进行中，有未提交文件"，而工作树是干净的，远程确实有那个提交。门禁全绿，冷读抓到。

**结论一：结构检查是必要的，但不充分。** 八个章节可以和一个矛盾和平共处。我后来把这句话写进了协议本身（`docs/limits.md` §2："最坏的失败不是红色的门禁，而是一份**全绿但自相矛盾的交接**"）。

那我自己呢？我给自己的仓库也做冷读，规则和上面一样：零上下文、只读四文件、逐条找矛盾。

- **v1：8 处**。git 归属警告过期了；验收条件漏了冷读这一步；`PROJECT.md` 和 `HANDOFF.md` 对"测试 → 冷读 → 提交/打 tag → 写文章"的顺序有四种写法；`last_verified_command` 只记了 `ahp check`，但实际验证还跑了 `npm test`；"把文档写完"这种含糊表达，而文档其实已经写完了；漏了一句说明 `PROJECT.md` 的状态块是**派生的**、不能手改。
- **v2：3 处**。发布顺序含糊（还没提交却要求 clean tree）；本地 tag 还是远端 tag 说清了；下一单元在哪里打开说清了。
- **v3：5 处**。更细的语义不一致。

8 处、3 处、5 处，**全部是文档问题**。代码没问题，交接文本有问题。

这正是 AHP 要抓的失败，也说明冷读不是一次性动作——**它要迭代，每一轮都有产出**。

### 那些矛盾，最后都去了哪

冷读的价值不在"发现"，在"发现之后不许它第二次发生"。学习项目那 12 处矛盾，逐条落到了两个地方之一——**一条门禁断言**，或者**一份写明理由的"接受，不修"**。

先说真正变成了门禁的三条，因为它们的原话和门禁检查的东西几乎一样：

| 冷读发现的矛盾 | 落点 | 门禁实际检查什么 |
|---|---|---|
| `current_file` 与正文 §3 互相矛盾 | `HANDOFF_BODY` | §3 说 none 时 `current_file` 必须为 none |
| 状态是 `ACTIVE` 但租约已过期 | `LEASE` | `ACTIVE` 必须有未来的 `lease_until`；`PAUSED`/`COMPLETE` 不许留残留 |
| 最后验证命令写的是生命周期命令（`ahp pause`） | `VERIFY_COMMAND` | `last_verified_command` 不能是 start/pause 这类命令 |

剩下的**没有**变成门禁，不是因为不重要，是因为**没有一条能可靠地机器检查**：

| 冷读发现的矛盾 | 为什么机器检查不了 |
|---|---|
| 同一个项目里有三套不同的验证命令 | `VERIFY_COMMAND` 只看**一个字段**合不合法，看不见三处文档各说一套 |
| 验收标准散在两个文件、数量还对不上 | `HANDOFF_BODY` 只要求 §4 有编号动作、`next_action` 非空，不核对验收条数 |
| 摘要的"最后更新"表头比它最新一条记录还早 4 天 | `HANDOFF_FRESH` 只看 §4–§6 的日期年龄（阈值 21 天），不比对表头与条目 |
| `INDEX.md` 一处写"地图和状态"、一处写"只放地图" | `INDEX_MAP` 匹配的是**动态状态行**，"地图和状态"这种措辞它不认识 |

这四条被写成书面的接受，而不是硬凑成一条正则门禁。**凑出来的门禁会制造假绿，这是整套东西最讨厌的事。**

## 三、更糟的：验证层自己会撒谎

上面那些矛盾，好歹还能被冷读抓到。真正让我后怕的是另一类问题：**负向测试告诉我门禁坏了，其实是我的测试坏了。**

这一节四个案例，全部来自 `docs/lessons-from-production.md` §3 和 `docs/case-studies.md`。

### 3.1 夹具没到阈值，"红"的测试是假的

新鲜度门禁在超过 21 天时失败（阈值来自 `ahp.config.json` 的 `freshness.handoffDays`）。我的负向夹具造了一个 **20 天** 的 `HANDOFF.md`。

20 天 < 21 天，所以门禁**正确地**只报了个 WARN，没报 FAIL。我的测试期望 FAIL，于是"红"不起来。

看起来像门禁失灵，其实是夹具不合格。修法两个：把夹具放到明显越过阈值的位置（比如 40 天），或者别去断言那句人类可读的文案。

### 3.2 门禁读的是真仓库，不是夹具

这条更阴。夹具写在临时目录里，`git status` 和 `git log` 却跑在**真实项目**上。真实仓库当时是脏的，于是门禁把自己跳过了——报告"通过"。

我的测试报"没红"，而门禁逻辑完全正确。

修法：测试要建一个**临时 git 仓库**，把 root 显式传进去，每个 git 命令都用那个 root。**隔离不是测试的便利，是测试的一部分。**

### 3.3 断言文案，而不是断言门禁

门禁输出 `21 days`，测试找 `20 days`。测试红了，门禁是好的。

反过来更危险：文案一改，测试**悄悄通过**，门禁从此不再被真正触发——它变成一个永远不会失败的装饰。

修法：断言**门禁 ID + 状态**（`LEASE` / `FAIL`），数字部分用正则，退出码也一起断言。

### 3.4 一个叫 `--check` 的命令，居然会写文件

这条最离谱，也最该单独拎出来说。

一个备份脚本，参数叫 `--check`。它的行为是：先把源文件复制进备份目录，**然后**才进入比较分支，最后把 git 差异报出来。结果：它报告"10 处差异"，同时在备份仓库里留下 10 个未提交改动。

一个会写的检查不是检查，它是一次伪装成检查的迁移。

修法：比较先做，写入放在显式的非 check 分支后面；并且**用 `git status` 在 `--check` 前后各验一次**。

AHP 自己的 `check` 也有同一条纪律：门禁必须只读，`sync` 才写。所以我加了一条约定——任何"验证"命令跑完，工作树必须和跑之前一样。

## 四、我改了什么

五个动作，都是把"发现"变成"不能再犯"。

**1. 单一当前状态源。** 动态状态只住在 `HANDOFF.md` 里。`INDEX.md` 只做地图，所以 `INDEX_MAP` 门禁专门检查它有没有长出状态行。长期决策归 `PROJECT.md`。同一个事实不允许在三个文件里各有一份。

**2. 派生，而不是复制。** `PROJECT.md` 顶部那个状态块是 `ahp sync` 从 `HANDOFF.md` 生成的，不是手写的。手写就一定会漂移，所以有 `ahp sync --check` 专门盯着它漂。**能用工具生成的字段，就不要靠纪律维持。**

**3. 负向测试就是产品。** 12 条门禁，每条都有必须变红的夹具。一个门禁如果没有能失败的测试，它就只是一句声明。这条规矩的代价是我要多写负向测试（v0.1.0 时 15 个，现在 20 个）；回报是每条门禁都还活着。

**4. 隔离 git 夹具。** 见 3.2。

**5. 冷读进协议。** 冷读不是"读一遍 README 总结一下"，而是让一个零上下文的会话回答五个具体问题。**每一条矛盾必须二选一：变成一条门禁断言，或者写成一份"接受，不修"并写清理由。** "读一遍就算了"是禁止的。

还有一条来自外部审计的铁律，我原样照抄：**每条 findings 要么变成门禁/测试，要么变成一份写明理由和重新评估触发条件的书面接受。** 这一条让"我知道有问题"不会烂在脑子里。

## 五、这次没有解决的（也是我不敢承诺的）

写到这里，最容易被理解成"装个 AHP，你的记忆系统就安全了"。不是。写清楚边界，比写清楚卖点重要。

- **结构绿 ≠ 语义对。** 门禁能看见文件在不在、字段合不合法、时间戳有没有倒序、租约有没有过期、派生块有没有漂、索引里有没有混进状态、密钥有没有漏。它**看不见** `next_action` 是不是正确的下一步，看不见两次验证是不是真的跑过，看不见两个文件在叙述层面有没有打架，看不见一条记忆在现实世界里是否还成立，也看不见这个单元是不是被人真的接受了。**最坏的失败不是红灯，是一份全绿但自相矛盾的交接。**
- **两个模型同意，不是证据。** 我现在的流程是"一个主写 + 一个独立审查"：审查者只读，带 `file:line` 和证据回结论，主写逐条裁决——修掉、加测试/门禁、或者写明"接受不修"和理由。审查者**不能合并**，测试和代码永远压过模型共识。两个模型都说"没问题"，也可能只是它们犯的是同一个错。
- **AHP 不是记忆库。** 它不替代 Mem0 / Letta / Zep，不做向量检索，不做长期记忆抽取。它就是四个文件、一个状态机、一组只读检查、一次冷读。
- **AHP 不是权限系统。** 租约是软锁，不是认证。它挡的是手滑和低级并发，不是恶意行为。
- **AHP 不是安全保证，更不是攻击工具。** 它不接触任何线上目标，不"自动挖洞"。它只是让交接状态更难骗过下一个人。

还有一条我特意留在文档里的：`docs/limits.md` 不是 README 底下的小字免责，它是**协议的一部分**。会让人误以为有保护的东西叫免责声明，是不诚实的。

## 七、一句话

如果这套东西只能留下一句话，我希望是这个：

> **交接系统不是记忆系统，是"真相维护系统"。**
> **一旦它的检查不再可能失败，它就变成了又一个漂移源。**

而对你来说，最便宜的起点不是装什么工具，是**下一次交接的时候，让一个没有上下文的人来读你的状态文件**。他读不懂的地方，就是你的系统正在骗你的地方。
