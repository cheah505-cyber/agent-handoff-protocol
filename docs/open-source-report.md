# Agent Handoff Protocol 开源搭配报告书

版本：v0.1 ｜ 日期：2026-11-25 ｜ 适用对象：一个人、有 AI/Agent 使用经验、想把“记忆治理”做成开源背书与副业入口的开发者。

---

## 0. 摘要

AHP（Agent Handoff Protocol）是一套**仓库内的、可机器检查的交接协议**：四个核心文件、十二条门禁、一次冷读。它不解决“记住更多”，它解决“当前状态是否可信、换人后能否接上”。

这份报告回答三件事：

1. 这套东西怎么开源，才既有技术 credibility，又不会变成维护黑洞。
2. 开源之后，如何搭配 2a 主业背书、2b AI 安全评估、2c 内容、2d 团队版、2e 模板，形成一个有先后顺序的组合，而不是五件事同时做。
3. 90 天内怎么验证，什么情况下停。

**核心判断：**

- **2a（portfolio）是最稳的回报**，应该在 v0.1 发布后立刻使用。
- **2c（内容）是杠杆**，一篇文章可以让 2a 和 2b 同时受益；但不要做成 content farm。
- **2b（AI 记忆安全评估）是天花板最高的副业**，但不适合现在卖；等你有 1–2 个案例、并且网安学习进入阶段 2/5 之后再接。
- **2e（模板）是 lead magnet，不是收入**；免费或 ¥99，用来换邮箱/关注，不要优化它。
- **2d（团队版/SaaS）最后做**；只有 3 个以上团队主动问，或者 1 个团队愿意付 ¥3 万以上，才值得写代码。

一句话：**先把验证层做可信，再把故事讲出去；先卖服务/背书，再卖产品。**

## 1. 系统是什么，不是什么

### 1.1 是什么

- 一个 repo-local 的交接协议：`AGENTS.md`、`INDEX.md`、`PROJECT.md`、`HANDOFF.md`、`memory/`。
- 一个 12 条门禁的只读检查器：状态、租约、时间、验证命令、正文、索引、派生块、记忆链接、密钥、git 状态。
- 一个派生同步器：`ahp sync` 从 `HANDOFF.md` 生成 `PROJECT.md` 的状态块。
- 一个脚手架：`ahp init` 复制模板到新项目。
- 一套负向测试：22 个测试（v0.1.0 快照；现为 27，其中 19 个负向夹具），证明每条门禁对坏形态敏感。

### 1.2 不是什么

- 不是 Mem0/Letta/Zep 的替代品；它不做向量检索、不做长期记忆抽取。
- 不是多 Agent 编排框架；它只规定交接契约。
- 不是权限系统；租约是软锁，不是认证。
- 不是“自动挖洞”工具；它不接触任何线上目标。
- 不是“装上就安全”；结构绿不等于语义对。

### 1.3 差异化

大多数 Agent memory 项目在比“记得多、检索准”。AHP 在比“**记忆是否可信、是否过期、是否互相矛盾、换人能否接上**”。这是一个更窄、更安全、更容易被工程团队理解的品类。

## 2. 为什么现在做

### 2.1 真实的失败模式

对一个生产项目和一个学习项目的只读审计，提炼出六类失败：

1. 中断漂移。
2. 事实源混乱。
3. 状态不可验证。
4. 并发覆盖。
5. 审查走形式。
6. **门禁全绿，文件互相矛盾。**

第 6 类最危险，因为它杀死了“检查”的可信度。

### 2.2 真实的数据

- 生产项目：70+ 记忆文件、279 条 wiki 链接、211 KB `HANDOFF.md`、185 KB 长期摘要、5 处派生镜像。
- 学习项目：7 个核心文件、3 个记忆文件、13 条门禁；冷读在四个文件里找到 12 处矛盾，而门禁是 0 FAIL。
- 负向测试：一个 20 天夹具对 21 天门禁；一个 git 门禁跑在真实脏仓库上；一个测试断言“20 天前”而实际输出“21 天前”。
- 一个 `--check` 备份脚本在检查前先复制文件，留下 10 个未提交变更。
- 一个 `ACTIVE` 租约过期 34 分钟，项目级门禁没有检查租约。

这些不是编的案例，是 AHP 的测试来源。

AHP 自己也做了一次冷读：12 条门禁全绿的情况下，冷读找出 8 处文档不一致——git 归属警告过期、验收漏了冷读、`PROJECT.md`/`HANDOFF.md` 对“测试→冷读→提交→文章”的顺序有四种写法、`last_verified_command` 漏记 `npm test`、文档完成度含糊等。第二次冷读又抓到发布顺序（未提交却要求 clean tree）和“本地 tag 还是远端 tag”两处含糊。代码没问题，交接文本有问题；这正是 AHP 要抓的失败，也说明冷读要迭代。

### 2.3 市场时机

- 编码 Agent 从“单次补全”变成“多会话、长任务、多 Agent”。
- 团队开始遇到“Agent 把 README 写歪了”“两个 Agent 互相覆盖”“新会话重做已完成工作”。
- 现有工具解决检索，不解决交接纪律。
- AI 安全开始从“模型越狱”扩展到“Agent 记忆投毒、工具滥用、供应链”。

AHP 正好卡在“工程纪律”和“Agent 安全”之间。

## 3. 资产盘点

### 3.1 代码资产

- `bin/ahp.mjs`：CLI（init/check/resume/sync/test）。
- `lib/gates.mjs`：12 条只读门禁。
- `lib/sync.mjs`：派生状态块。
- `lib/init.mjs`：模板脚手架。
- `tests/`：22 个正/负向测试，隔离临时项目 + 临时 git 仓库。
- `templates/`：可直接复制的项目模板。
- `docs/`：设计、限制、安全、案例、生产教训、本报告。

### 3.2 认知资产（更值钱）

- 五根因框架：时间戳可脱内容、手写同步必漏、多源无单源、角色契约只查结构、fail-open 制造假信心。
- 假绿分类：同文件矛盾、时间戳同步、门禁自跳过、夹具阈值错、检查会写、语义盲区。
- 冷读方法：零上下文、四文件、五问、逐条变门禁或书面接受。
- 外部 findings 铁律：每条 findings 二选一——变门禁断言，或书面接受不修+理由。
- 轻量移植经验：生产系统 70+ 文件，学习项目 7 文件，证明可以裁剪而不丢核心。

### 3.3 不具备的资产

- 没有大规模用户、没有社区、没有品牌。
- 没有 AI 安全实战案例（SRC/CVE/评估报告）。
- 没有团队、没有销售、没有法务。
- 没有经过外部用户验证的“真实痛点频率”。

这些决定了：**先做开源背书和服务，不要先做 SaaS。**

## 4. 开源策略

### 4.1 定位

**Agent Handoff Protocol：给编码 Agent 的交接治理协议。**

不要叫“memory system”。叫 memory 会被拿去和 Mem0/Letta/Zep 比检索；叫 handoff 是另一个品类，竞争少，问题真。

### 4.2 许可证

MIT。协议和 CLI 开源；如果要商业化，商业化的是团队工作流、支持、审计，不是 markdown 本身。

### 4.3 仓库结构

```
README.md (EN) / README.zh-CN.md
SPEC.md
AGENTS.md / INDEX.md / PROJECT.md / HANDOFF.md
bin/ahp.mjs
lib/{gates,sync,init,handoff,config}.mjs
templates/
tests/
docs/{design,limits,security,lessons-from-production,case-studies,open-source-report}.md
memory/
.github/workflows/check.yml
LICENSE
```

### 4.4 30 小时开源冲刺

维护（修门禁/测试/备份）另算 2–3 天；不要混进 30 小时，否则一定超时。

| 时间 | 产出 |
|---|---|
| 6h | 抽取 lite core，去业务化，确认 4 文件 + 12 门禁 |
| 8h | CLI、测试、CI、init 脚手架、负向夹具 |
| 8h | README、SPEC、design/limits/security、案例 |
| 4h | war story 文章初稿 |
| 4h | 分发（掘金 / 先知 / 安全客 / dev.to / LinkedIn / r/LLMDevs）+ 修反馈 |

**Kill criteria：** 30 小时到点没有真实用户/issue/转载，或明显耽误网安阶段 1 → 停，保留 repo 作 portfolio。

### 4.5 发布前必须做的事

1. `npm test` 全绿（22+）。
2. `node bin/ahp.mjs check` 0 FAIL。
3. 一次冷读：零上下文只读四文件，能答出当前状态/下一动作/风险；矛盾要么修，要么写进 `docs/limits.md`。
4. 仓库里没有客户数据、密钥、生产事实。
5. README 第一屏讲“为什么”，不是“文件列表”。

## 5. 2a：主业价值（最稳）

### 5.1 它证明什么

- 你会设计状态机，而不是只会写 prompt。
- 你会写门禁和负向测试，而不是只会“让 AI 跑一下”。
- 你会处理多 Agent 冲突、租约、派生同步。
- 你会做安全思维：fail-closed、最小权限、不可信输入、审计轨迹。
- 你会写文档和复盘，而不是只交代码。

### 5.2 简历写法

> Built AHP, a machine-checkable handoff protocol for AI coding agents: 12 read-only gates, 22 negative/positive tests, derived status sync, and a cold-read audit. Found 12 contradictions in a “green” memory system and fixed the verification layer.

### 5.3 面试叙事（STAR）

- **Situation:** 多会话 Agent 项目，交接靠聊天记录，状态漂移、重复劳动。
- **Task:** 让新会话只靠磁盘恢复现场，并且让“完成/暂停”可检查。
- **Action:** 四文件契约、12 门禁、派生状态块、负向测试、冷读；把每次审计发现变成门禁或书面接受。
- **Result:** 门禁可复跑；冷读从“答不上来”到“能指出矛盾”；测试从假阴性变成 22/22；形成可复用模板。
- **Reflection:** 最大的坑不是记忆，是验证层；green ≠ correct。

### 5.4 Demo 脚本（10 分钟）

1. `ahp init /tmp/demo`，展示四个文件。
2. `ahp check`，展示 12 条 PASS。
3. 手动把 `HANDOFF` 的 `last_verified_command` 改成 `ahp pause`，再跑，展示 `VERIFY_COMMAND` FAIL。
4. 把 `PROJECT` 状态块改旧，跑 `ahp sync --check`，展示 FAIL；`ahp sync` 后 PASS。
5. 讲一个真实假绿案例（20 天夹具/脏仓库/`--check` 写入）。

## 6. 2b：AI 安全评估（天花板最高，但别现在卖）

### 6.1 卖什么

**Agent Memory Security Review（AI 记忆治理评估）**：

- 记忆架构梳理：哪些文件自动注入、哪些可写、哪些跨 Agent 共享。
- 记忆投毒测试：低权限写入能否改变高影响动作。
- 过期事实测试：决策被推翻后旧记忆是否还在生效。
- 注入测试：记忆文件里的指令是否会被执行。
- 跨 Agent 信任测试：租约、覆盖、审计轨迹。
- 门禁测试：脏树/坏日期/缺文件是否会假绿。
- 写入测试：`check`/`verify` 是否会改状态。
- 交付：findings + 证据 + 修复 + 复测；不公开 exploit。

### 6.2 定价与交付

- 小团队/单应用：¥5k–15k，2–5 天。
- 海外/复杂 Agent：$1k–5k。
- 复测：¥2k–5k。
- 形式：远程 + 只读/测试环境；书面授权；NDA；不碰生产数据。

### 6.3 客户

- 用编码 Agent 的工程团队（Claude Code/Codex/Cursor/OpenCode）。
- 做客服/销售 Agent、RAG、内部 copilot 的团队。
- 安全服务商/众测团队（他们需要 AI 安全能力）。
- 出海 SaaS（英文报告，单价更高）。

### 6.4 时机

**不要现在卖。** 你现在是网安阶段 0/1，缺实战案例；先：

1. 用 AHP 自己做一次公开的“记忆安全自评”。
2. 写一篇“Agent 记忆是攻击面”的文章。
3. 在网安阶段 2/5 后，做 1–2 个免费/低价案例，换 testimonial。
4. 再开始报价。

### 6.5 合规

- 只测授权系统；记忆文件不是授权。
- 测试账号/合成数据；不导出真实用户数据。
- 不公开 exploit；给修复窗口。
- 不卖“入侵工具”；AHP 是防御协议。

## 7. 2c：内容（慢，但复利）

### 7.1 两篇文章

**文章 1（AI 工程圈）：**

> 《0 FAIL，12 处矛盾：我的 Agent 记忆系统如何骗了我》

结构：

1. 我做了四文件 + 13 门禁，全绿。
2. 零上下文冷读，找出 12 处矛盾。
3. 负向测试也有假阴性：20 天夹具、脏仓库、21 天消息。

6. 开源 repo + 冷读清单。

渠道：掘金、V2EX、即刻、dev.to、Hacker News（英文版）。

**文章 2（安全圈）：**

> 《Agent 的记忆是攻击面：投毒、过期事实与假绿门禁》

结构：

1. 记忆是下一轮 Agent 的“信念状态”。
2. 四类攻击：投毒、过期、hook 注入、跨 Agent 信任。
3. 三类验证层攻击：fail-open、check 写入、模板供应链。
4. 防御：不可信输入、最小权限、只读检查、冷读、审计。
5. 评估清单（2b 的 lead magnet）。

渠道：先知、安全客、LinkedIn、dev.to、r/LLMDevs。

> **2026-11-26 实测修正：** FreeBuf 对自动化和用户浏览器都返回 405（放弃）；V2EX 需邀请码；r/netsec 规则 9 禁 AI 生成内容；Hacker News 注册关闭。实际已发渠道见 `docs/publish-plan.md` 顶部「已发布清单」。

### 7.2 节奏

- 两周一篇，不追热点。
- 每篇绑定一个 repo issue/test/案例；没有真实素材就不写。
- 一篇文章只做一个 CTA：repo、清单、或评估咨询。

### 7.3 不要做

- 不做“AI 暴富”“三天学会”类内容。
- 不刷量、不买粉。
- 不把 epl-pro 的业务数据/密钥写进文章。

## 9. 2d：团队版/SaaS（最后）

### 9.1 触发条件

- 3 个以上团队主动问“有没有团队版”。
- 或 1 个团队愿意付 ¥3 万以上做私有部署/定制。
- 或你的开源 issue 里反复出现“多 Agent 租约/审计面板/CI 策略”。

### 9.2 功能

- 多 Agent 租约与冲突检测。
- 审计面板：谁改了哪个记忆、何时、为什么。
- CI 策略包：按团队规则启用/禁用门禁。
- SSO/权限/私有部署。
- 适配器：GitHub/GitLab/Jira/Linear/飞书。

### 9.3 定价

- ¥99–299/seat/月，或 ¥3 万–10 万/年私有部署。
- 只做“能收到钱”的功能；不做通用 dashboard。

### 9.4 风险

- 支持负担、销售周期、与现有 AppSec 平台竞争。
- 一个人做 SaaS 容易变成 7×24 运维。
- 没有 3 个付费客户前，不要写团队版代码。

## 11. 90 天路线图

### 第 1–2 周：可信的 v0.1

- 修 12 条门禁的测试隔离。
- 通过 22+ 测试和一次冷读。
- 提交 git、打 tag `v0.1.0`。
- 写 README 第一屏和 10 分钟 demo。

**验收：** 一个陌生人按 README 能在 10 分钟内跑通 `init` + `check`。

### 第 3–4 周：发布与内容

- 发文章 1（AI 工程圈）。
- 发文章 2（安全圈）。
- 提交到 1–2 个 awesome list / newsletter。
- 收集 issue，不急着做功能。

**验收：** 至少 20 个 star、3 个真实 issue/评论、1 个外部使用反馈。

### 第 5–8 周：案例

- 给 1–2 个团队做免费/低价“记忆治理评估”。
- 交付报告 + 复测；换 testimonial。
- 把评估清单变成可下载的 lead magnet。

**验收：** 1 个可公开的案例（匿名也可），1 个愿意付费的意向。

### 第 9–12 周：第一次收费

- 报价 ¥5k–15k；只接授权、可控范围。
- 交付 2–5 天；不承诺“找出所有问题”。
- 复盘：时薪、获客成本、交付时间。

**验收：** 1 笔付费，或明确的市场“不”信号。

## 12. 指标与 kill criteria

### 12.1 领先指标

- README → `init` 的转化（issue/评论）。
- 外部 issue 的质量（是否真实使用，不是“求 star”）。
- 文章读完/收藏/转发，不是单纯阅读量。
- 冷读/评估的预约数。

### 12.2 滞后指标

- 付费评估数量。
- 每单交付小时数。
- 时薪（目标 > ¥300/h）。
- 开源维护时间/月（目标 < 10h）。

### 12.3 Kill criteria

- 90 天没有 1 个真实外部使用/issue → 开源降级为 portfolio。
- 维护 > 10h/月且没有收入 → 冻结功能，只修 bug。
- 2b 连续 3 个月没有付费意向 → 转内容/代码审计，不硬卖。
- 明显耽误网安阶段 1/2 → 停 30 天。

## 13. 开源项目自身的维护

- **每周：** `npm test` + `ahp check`；处理 issue；不合并没有测试的 PR。
- **每月：** 一次冷读；检查 docs 与实现是否一致；清理过期 issue。
- **每季度：** 评估是否加门禁；删除产生 alarm fatigue 的检查；更新 roadmap。
- **发布：** semver；`v0.1.x` 修 bug，`v0.2` 加可选功能；breaking change 给迁移说明。
- **安全：** SECURITY.md、私密报告渠道、无密钥、依赖为零。
- **社区：** issue 模板、PR 模板、行为准则；不追求大社区，先追求 3 个真实用户。

## 14. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 过度工程 | 维护吃掉学习时间 | 12 门禁封顶；30h 时间盒；kill criteria |
| 假绿 | 声誉受损 | 冷读；负向测试；docs/limits 明示 |
| 内容像营销 | 技术圈反感 | 用真实失败/数字；不承诺“自动挖洞” |
| 2b 无案例 | 卖不动 | 先免费/低价 1–2 单；阶段 2/5 后再报价 |
| 法律 | 未授权测试/数据 | 书面授权；测试环境；NDA；不碰生产 |
| 竞争 | Mem0/Letta/Zep/大厂 | 不做检索；做 handoff governance；做中文服务 |
| 时间 | 副业挤占主业 | 每周上限 10h；阶段 1 优先 |

## 15. 附录

### 15.1 门禁与测试矩阵

| 门禁 | 负向测试 | 主要失败形态 |
|---|---|---|
| `CORE_FILES` | 删除 AGENTS.md | 交接链断裂 |
| `HANDOFF_SCHEMA` | 非法 status | 状态不可读 |
| `HANDOFF_TIME` | 验证时间晚于交接 | 时间伪造 |
| `LEASE` | 过期 ACTIVE / PAUSED 残留 | 并发覆盖 |
| `VERIFY_COMMAND` | `ahp pause` | 假验证 |
| `HANDOFF_BODY` | 删除 §4 | 交接不完整 |
| `HANDOFF_FRESH` | 40 天旧日期 | 现场停滞 |
| `INDEX_MAP` | 动态状态行 | 索引变状态表 |
| `PROJECT_SYNC` | 派生块过期 | 长期记忆漂移 |
| `MEMORY_LINKS` | 死 hook / 悬空链接 | 记忆库腐烂 |
| `SECRETS` | 假 token | 凭据泄漏 |
| `GIT_STATE` | 脏树 / 提交日不匹配 | 时间戳脱内容 |
