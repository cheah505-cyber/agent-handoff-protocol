# v0.2 candidates: what a check must clear before it ships

This is not a roadmap commitment. It records three checks that readers proposed, what a local spike showed about each, and the rule that decides whether one enters the product. Present state: none of them is implemented, and the suite stays at 12 gates / 27 tests.

The rule exists because a check that cannot fail is worse than no check: it turns a green result into a claim it did not earn (`docs/limits.md` §3).

## Admission rule

A candidate enters v0.2 only if all four hold:

1. **No format change**, or the format change has been accepted first. A gate cannot require a field that the protocol does not define.
2. **A fixture that must turn red.** The same standard as every existing gate; a check without a failing fixture is a suggestion.
3. **Zero false positives on this repository**, measured, not assumed.
4. **An external ask.** A reader or a real repository hit the failure. Our own preference is not demand.

Candidates that fail (1) are not rejected; they are sequenced: decide the format, then build the check.

## 1. Duplicate frontmatter key

**Proposed by** gimalay in the war-story comments (`3mhg4`): keep a moving value in one file's frontmatter, let other files link to it instead of restating it, and fail when a second file carries the same key.

**What it can see.** Only frontmatter. Two files that both declare `status` or `updated_at` are detected; two paraphrases of one policy in prose are not. The historical "acceptance criteria in two files with different counts" lived in prose, so this check would not have caught it.

**Spike.** A 20-line script (below) was run on the four core files and on a two-file fixture with `status` in both:

```
AHP four core files  → no duplicate frontmatter keys
synthetic fixture    → status: A.md, B.md
```

**Verdict.** Meets rules 1–3 and has the external ask (rule 4). Ship in v0.2 as a **WARN**, scoped to the four core files, with an allowlist for keys that legitimately repeat (`type`, `date` in review notes — outside the core scope anyway) and one negative fixture. Do not make it a FAIL: a deliberate second copy may be the point in a migration.

```js
// spike, not product code: duplicate frontmatter keys across given files
import fs from "node:fs";
const files = process.argv.slice(2);
function keys(p) {
  const t = fs.readFileSync(p, "utf8");
  const m = t.match(/^---\n([\s\S]*?)\n---/);
  if (!m) return [];
  return m[1].split("\n").filter(l => /^[A-Za-z_][\w-]*:/.test(l)).map(l => l.split(":")[0]);
}
const seen = new Map();
for (const f of files) for (const k of keys(f)) {
  if (!seen.has(k)) seen.set(k, []);
  seen.get(k).push(f);
}
const dups = [...seen].filter(([, v]) => v.length > 1);
console.log(dups.length ? dups.map(([k, v]) => `${k}: ${v.join(", ")}`).join("\n") : "no duplicate frontmatter keys");
```

## 2. Superseded-by pointer

**Proposed by** mickyarun (`3mg2o`): derivation only corrects state if the superseding write names what it supersedes. Otherwise two versions of one decision are both live, both dated, both plausible.

**Blocker.** There is no field to check. `superseded_by` does not exist in the protocol; the word "superseded" appears only in prose. A checker would have to guess which sentence replaced which — exactly the kind of language-model judgment that is a review prompt, not a gate (`docs/design.md`).

**Verdict.** Fails rule 1. Two ways forward, both format decisions:

- Add `superseded_by: "PROJECT.md#<anchor>"` to a decision entry, and have the gate check that the target exists and is newer. Cheap once the field exists; useless before.
- Do nothing and keep it a cold-read question: "which two statements disagree, and which one replaced the other?"

Decide the format before writing the check. Until then, the candidate stays here.

## 3. Licensing / authority declaration

**Proposed by** mickyarun in the same comment: instead of classifying input as trusted or untrusted, have the standing task name which arguments it licenses from untrusted input. Relaying a message body is licensed; acting on an account number inside it never was.

**Why it is not a gate.** AHP performs no actions, so there is no interception point to check. The honest form is a template field in `HANDOFF.md` — for example `licensed_arguments: "read: issue text; never: payment fields"` — plus a review question. A gate that looked for the word "licensed" would pass an empty promise, which is the failure mode this project exists to prevent.

**Verdict.** Template change, not a check. Fails rule 1 as a gate; viable as a schema addition in v0.2 if a real task needs it.

## What would change these decisions

- A real repository hitting the duplicate-key failure with a key the check misses (for example two prose copies) would show the check is too narrow to matter.
- A real task that needs to cite authority in its handoff would justify the licensing field.
- A user asking for a superseded-by convention would settle the format question in one line.
